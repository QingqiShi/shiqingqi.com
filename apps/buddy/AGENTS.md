# Buddy

Buddy (搭子, buddy.qingqi.dev) shows a person's Claude pet, 小苗 (Miao), live on a phone. Anyone can sign up. A Mac signs and uploads its pet state, Redis keeps it, and the page `/u/[user]` and `GET /api/v1/u/[user]` show it, to anyone once the owner made the page public. A daily cron copies each Mac's days into Postgres.

- Ports: the app is `node ../../scripts/get-worktree-port.mjs 400` (or `BUDDY_PORT`), its PGlite database `… 2633`.
- `src/pet/types.ts` holds the contract: `PublicPetState` is the read API's JSON and the page's input. `src/pet/` imports nothing from the rest of the app.
- Accounts (`src/server/db/schema.ts`): `accounts` (`name` is the `[user]` of `/u/[user]` and never changes; `email` is the confirmed sign-up address; `is_public` is false until the owner turns it on; `visitor_fed` and `visitor_patted` are the cron's copy of the care counts), `passkeys`, `sessions`, `email_codes`, `sign_ups`, `recoveries`, `machines` (each Mac's Ed25519 public key; `machine_id` is unique over all accounts; removing the Mac on `/macs` sets `revoked_at`). Every row carries the account id (a uuid); only URLs, the upload signature and the Redis keys that a public read starts from use the name. Pass the user id from the session, never from a request body.
- Auth (`src/server/auth/`) is a port of Finance's: passkeys (`@simplewebauthn`, the host is the RP ID), a five-minute sealed challenge cookie, and a session token whose hash is in `sessions`. Sign-up: `POST /api/auth/sign-up` emails a six-digit code and a link (30 minutes, five tries, the code bound to the asking browser by a sealed cookie); the code (`/sign-up/code`) or the link opens `/sign-up/[token]`, where the person only saves a passkey; the server makes the account name itself (8 random lowercase letters and digits, retried on a collision, matching `account-name-pattern.ts`), so no one picks a name and sign-up reveals no name. For an address that has an account, the same request emails a recovery link instead and answers the same. Recovery: `POST /api/auth/recovery` answers the same for every address and emails the code after the response; `/recover/[token]` saves a new passkey, deletes the old ones and ends every session. Rate limits as in Finance (fixed windows in the store): every auth POST 10 a minute per IP; sign-up and recovery requests 10 an hour per IP and 3 an hour per address.
- Email (`src/server/email/`, as in Finance): `BUDDY_EMAIL_OUTBOX` writes each email as JSON to that folder; else `RESEND_API_KEY` and `BUDDY_EMAIL_FROM` send through Resend; else `next dev` writes to `apps/buddy/.buddy-outbox/`, which is where a local sign-up finds its code.
- Visibility: the owner's `/u/[name]` has a Public page switch (`POST /api/account/visibility`). To anyone else a private page, and its read API, answer exactly as a name that no account has (404). The owner's page reads with `includePrivate` and refreshes from `GET /api/account/pet`; only a visitor with a session cookie makes the page read Postgres.
- Sign in as an agent: `pnpm --filter buddy buddy:session` while `pnpm dev` runs, then set the cookie it prints on `http://localhost`. It signs in as the oldest account; `-- --name <name>` picks another, such as a fresh one that has no Mac yet.
- Connect a Mac (`src/server/connect/`, RFC 8628): the Mac sends `POST /api/v1/connect` `{ publicKey, name }` and gets `{ requestId, code, url, expiresIn: 600, interval: 5 }`; the owner opens `url` (`/connect?code=…`), signs in, checks that the code is the one on the Mac, and taps Connect (`POST /api/connect/decide`); the Mac polls `GET /api/v1/connect/[requestId]` for `pending`, `approved` (with `user` and `machine.id`, which it signs uploads with), `denied` or `expired`. A request lives 10 minutes in Redis, and its answer 10 more. Starts are limited to 10 per IP per 10 minutes, polls to 20 a minute per request and 120 per IP.
- Redis (`src/server/store/buddy-keys.ts`): no write depends on data that another writer wrote, so there is no Lua script and no compare-and-set; merging happens only when reading. Postgres stays the truth, and `src/server/machines/make-machine-registry.ts` writes Redis after each change there: `buddy:user:<name>:public` (the account id, only while the page is public; the toggle sets or deletes it), `buddy:user:<name>:macs` (a set of the account's Macs that were not removed; a Mac that stopped uploading stays, so its days still count) and `buddy:mac:<id>:key` (the Mac's account and public key, sealed with an HMAC by `BUDDY_AUTH_SECRET`, so a write to Redis alone cannot connect a Mac). Only the Mac's own signed uploads write `buddy:mac:<id>:snapshot`. Only the care route writes `buddy:user:<name>:care:fed` and `…:care:patted`, with INCRBY, which adds and needs no compare-and-set; the cron adds to them only to restore a lost count. Each snapshot holds the Mac's whole history, so a Mac must keep one machine id: connecting the same key again gets the id back, and removing a Mac (`POST /api/machines/remove`) deletes its key, its set entry and its snapshot, so that a later connect, under a new id, does not count its days twice. The connect flow's requests and the rate limits are keys with a TTL.
- Upload (`src/server/upload/`, two commands): `handleUpload` checks the size (512 KB, counted, not read from Content-Length), then GETs the Mac's key, its snapshot and the two care counts in one MGET, opens the key (a missing or bad one is 401, and it never reads Postgres), checks the signature (`Buddy-Machine`, `Buddy-Signature` over the user, the machine and the body's SHA-256), then the strict body schema, which refuses any key it does not name, so a PR title or a repository name never reaches the store. The body's `at` must be within 2 minutes of the server clock and newer than the snapshot's `at`, which refuses a replay. The new snapshot is the upload with each day the larger of the old and the new count (a day never shrinks) and only the last 24 hours of quota samples, plus `receivedAt`. It answers `{ "ok": true, "visitors": { "fed", "patted" } }`. Every auth failure gets the same 401. `signUpload` in `verify-upload-signature.ts` is how a client signs.
- Read (`src/server/snapshot/read-pet-state.ts`, two commands): SMEMBERS of the account's Macs, then one MGET of `buddy:user:<name>:public` and their snapshots, with `withVisitors` (the page and the read API, not the others read) also the two care counts (`visitors`, 0 when missing); without that key the answer is null, so a private page and an unknown name are the same 404. `combine-snapshots.ts` is pure and knows only the Macs: days are summed over the Macs, each account field (quota, GitHub, merges, party, time zone, level-up) comes from the Mac that saw it last (`quota.at` and `github.fetchedAt` where there are; otherwise the snapshot's `at`), and a Mac without the field has no say; the highest level and the pet counters take the largest; `updatedAt` is the newest `receivedAt`. The page caches its read for 30 s under the tag `buddy-pet-state:<name>`, which the toggle expires; the read API has `s-maxage=30` and no stale-while-revalidate, so a page made private leaves the CDN within 30 s.
- Others (`src/server/snapshot/handle-others-read.ts`): `GET /api/v1/u/[user]/others` is a read that a connected Mac signs (`Buddy-Machine`, `Buddy-At`, `Buddy-Signature` over the user, the machine and `Buddy-At`, which must be within 2 minutes of the server clock; `readMessage` in `verify-upload-signature.ts` is what a client signs). It answers the combined state of the account's other Macs, also for a private page, so that the Mac adds its own fresh days to theirs. It reads only Redis, and every auth failure, also for a private or unknown name, gets the same 401.
- Care (`src/server/care/`): the page's 「喂水」 and 「摸摸」 buttons, for visitors and the owner alike, play the feed or pat action and line at once, as the Mac's pane does, and `use-care-batch.ts` sends the presses in one `POST /api/v1/u/[user]/care` `{ "fed": 0–20, "patted": 0–20 }` (strict, at least one above 0) 2 s after the last press, at once when a kind reaches 20, and on pagehide (keepalive), with no retry. The route counts only on a page the caller may see, which is a public page, or a private one with its owner's session (only then does it read Postgres), and answers any other name with the read API's 404; a request that counts by the owner's session must come from the page's origin (else 403, as the other cookie POSTs); then 30 requests per IP per page per 10 minutes, then the INCRBYs in one pipeline, then 204. A tap on the scene stays local. The lines' `{fed}` and `{patted}` are the Mac's count plus the visitors'. `GET /api/v1/u/[user]/visitors` is a read that a connected Mac signs as for the others read (the same headers, signature and single 401, also for a private or unknown name; both go through `upload/authenticate-signed-read.ts`, which checks the time before it reads Redis): one MGET of the Mac's key and both counts, answered `{ "visitors": { "fed", "patted" } }` with `no-store`; the Mac asks at most every 15 minutes. No page shows a count.
- Store (`getBuddyBackend()`): Upstash Redis when `KV_REST_API_URL` and `KV_REST_API_TOKEN` are set; otherwise, outside Vercel, a memory store per process with the same keys. On Vercel without Redis the routes throw. `store/buddy-kv.test.ts` runs against a real Upstash Redis too when `BUDDY_TEST_REDIS_REST_URL` and `BUDDY_TEST_REDIS_REST_TOKEN` name one it may write to.
- `pnpm dev` starts a per-worktree PGlite database in `.buddy-db/`, migrates it, seeds the public account `qingqi` with the Mac `dev-mac`, and sets a local `BUDDY_AUTH_SECRET`, unless `BUDDY_DATABASE_URL` is set. Delete `.buddy-db/` to start over. Without Redis, `src/instrumentation.ts` also seeds the memory store with `dev-mac`'s key and the snapshots of two Macs (`dev/dev-fixture-uploads.ts`, only in development), so `/u/qingqi` shows a pet that is awake; it falls asleep 30 minutes after the seed, and a dev upload wakes it. When the dev database answers, it also copies the database's accounts and Macs in, as the cron does.
- Try an upload: while `pnpm dev` runs, run `pnpm --filter buddy buddy:dev-upload`. It signs a sample upload for `qingqi` from `dev-mac` with the dev key (`dev/dev-account.ts`), checks that the same upload again and a changed body get 401, and prints the upload's reply and today's tokens before and after. The dev key is public; only the local dev database holds it.
- Archive: `GET /api/cron/archive` (Vercel Cron, daily, `CRON_SECRET` bearer) upserts every day of every Mac's snapshot into `buddy_usage_days` with GREATEST per column, so a run is idempotent and also backfills. It copies each account's care counts into `accounts` (GREATEST, one UPDATE per 100 accounts), and adds the difference to a Redis count that is missing or smaller. Then it writes every public account, Mac set and connected Mac's key from Postgres into Redis again, and deletes the keys and snapshots of removed Macs and the keys of private accounts, so a lost Redis heals within a day. The archive is a cold copy: nothing reads it for the page, and it keeps a removed Mac's rows. It answers 503 without `BUDDY_DATABASE_URL`. Change `src/server/db/schema.ts`, then run `pnpm buddy:generate`; never edit an applied migration. Preview and production builds run `pnpm buddy:migrate` (`BUDDY_DATABASE_URL_UNPOOLED`, advisory lock), which skips with a warning when no database is set.
- Env for a deployment: `BUDDY_AUTH_SECRET` (set once; a random 32-byte value), `KV_REST_API_URL`, `KV_REST_API_TOKEN`, `CRON_SECRET`, `BUDDY_DATABASE_URL` and `BUDDY_DATABASE_URL_UNPOOLED`, `RESEND_API_KEY` and `BUDDY_EMAIL_FROM` for the sign-up and recovery email, and `LICENSED_FONTS_READ_WRITE_TOKEN` for the font. `BUDDY_DEMO_USER` names the account whose pet the home page shows, through the public read, so it shows only while that page is public; unset, or private, the home page shows the dev fixture's pet (`src/home-page/read-demo-pet-state.ts`). Adding a Mac or an account never needs an env change.
