# Assistant

The app has one user, the owner, and stores login, settings, push subscriptions, the hashes of capture tokens, sealed mailbox logins, what the models write (morning reports), to-dos, which the report agent and the owner both write, and what the agents do: `agent_runs` (each run's steps, with the summary of the model's thinking and tool inputs and outputs cut short, the model's last words, its tokens and, while it runs, what it is doing in `progress`) and `agent_actions` (each change to a mailbox, with the mail's Message-ID, subject, sender and folders, and each change to a calendar or a to-do, for an activity page and undo). These hold headers and the agent's words; mail bodies stay in the mailbox and are read from IMAP when a job needs them.

- Ports: the app is `node ../../scripts/get-worktree-port.mjs 300`, its PGlite database `… 2533`. `ASSISTANT_PORT=3000 pnpm dev` puts the app on 3000, the one localhost port the Google and Microsoft OAuth clients accept; stop `apps/web` first.
- `pnpm dev` starts a per-worktree PGlite database in `.assistant-db/`, migrates it, seeds one dev user, and sets local secrets, unless `ASSISTANT_DATABASE_URL` is set. Delete `.assistant-db/` to start over.
- Sign in as an agent: `pnpm --filter assistant assistant:session` while `pnpm dev` runs, then set the cookie it prints on `http://localhost` (a LAN host needs a Secure cookie). There is no sign-up: the owner's passkeys exist in production, and a lost passkey needs a passkey row written by hand.
- Vercel env: run `vercel link --project assistant --scope tuja-labs --yes` in `apps/assistant` once, then `vercel env run -e development -- <cmd>` there. The repo root is linked to `qingqi-dev`. A changed variable reaches production only with a new build, and the `ignoreCommand` in `vercel.json` cancels a Redeploy of a commit that did not change the app, so merge a change under `apps/assistant` instead.
- Data access: pass the user id from the session or the cron, never from a request body, and filter every query of a user table by `user_id` (`ownAccount` in `mail/accounts/own-account.ts` for one account). There is no row level security.
- Migrations: change `src/assistant/db/schema.ts`, run `pnpm assistant:generate`; write SQL drizzle cannot generate with `pnpm exec drizzle-kit generate --custom --name <name>`. Never edit or delete an applied migration: production has run them all. `0000_baseline` replaced the first 18 migrations; its journal `when` is that of the last one it replaced, and drizzle runs only migrations with a later `when` than the newest applied one, so databases that ran the old migrations skip it. A dev database from before the baseline that fails to migrate needs `.assistant-db/` deleted. Vercel runs them on preview and production builds. Previews use the Neon branch `preview`, which `assistant-reset-preview-db.yml` resets from production every day, without sign-in sessions, capture tokens, mail accounts and push subscriptions.
- Crons: add the route under `src/app/api/cron/`, build it with `makeUserCronHandler`, and list it in `vercel.json`. The proxy lets `/api/cron/*` through without a Referer; the handler checks `CRON_SECRET`.
- Mail: `src/assistant/mail/`. IMAP goes through the `MailboxSession` interface (`imap/types.ts`); `imapflowConnector` is the real one, `createFakeMailServer` the in-memory one for tests. The connector never sends CLOSE or a plain EXPUNGE, which remove mail that another client flagged `\Deleted`: before a RENAME or DELETE it selects INBOX read-only, and imapflow then has no open folder to CLOSE. A move is MOVE; on a server with UIDPLUS and no MOVE (iCloud) it is UID COPY, `\Deleted` and UID EXPUNGE of those UIDs only, never imapflow's `messageMove`, whose fallback without UIDPLUS is a plain EXPUNGE. The copy comes first and a failed removal takes off the `\Deleted` the move set. A failed move followed by another move can leave a duplicate in the destination; the app accepts this, because it never guesses that a mail in the destination is the copy, and a wrong guess removes mail. Never test against a real mailbox. Log in with `openMailboxSession` (`accounts/open-mailbox-session.ts`): when the server refuses an OAuth token, it refreshes the token and tries once more before the account goes to `reconnect`. A connect and 立即检查 run `checkAccount`, which reads the folder list and no mail. The page `/mail/[accountId]/[messageId]` (`mail/view/`, `mail-page/`), which to-dos, report lines and calendar events link to, reads one mail live by Message-ID from every folder, read-only with BODY.PEEK, and shows HTML in a sandboxed `srcdoc` frame whose CSP loads nothing; `mailFrameDocument` also takes out `<meta>`, `<link>`, `<base>` and `<iframe>`, which can load past a CSP.
- Local OAuth: Google and Microsoft accept only `https://assistant.qingqi.dev` and `http://localhost:3000` callbacks, so run `vercel env run -e development -- env ASSISTANT_PORT=3000 pnpm dev` to get the client ids.
- Agents: `src/assistant/agent/`. The instructions of the organise and report agents start with `MAIL_WORKFLOW` (`mail-workflow.ts`), which tells each how the two work together; change it when that flow changes. `runAgent` (`run-agent.ts`) runs one task for one user with AI SDK `generateText`, tools and `stopWhen` (a step cap and the cron's `endsAt`), and writes `agent_runs`. Tools are framework-free `agentTool`s (`agent-tool.ts`), so an MCP endpoint can wrap them too; a refusal (`ToolRefusal`) or a failed call goes back to the model as `{ error }` and never stops the run. Only tools with `loadUpFront` are in the model's context from the start; `toAiTools` defers the rest (`deferLoading`) and adds Anthropic's BM25 tool search, which loads them when the model looks for them; `runAgent` names them in the instructions, because the model does not know of them otherwise. The API needs at least one tool that loads up front, and the cache breakpoint on the last message still caches every step, because a found tool is added in the conversation, not in the prefix. The mail tools hold every guardrail, not the prompt (`mail/create-mail-tools.ts` puts them together, with `create-mail-folder-tools.ts`, `create-mail-change-tools.ts`, `list-mail.ts` and `locate.ts` beside it): mail is only moved; no tool deletes mail or sends; never into Trash, Sent, Drafts or `\All`/`\Flagged`/`\Important` (Junk is allowed, `destination-refusal.ts`); a folder is deleted only when it holds no mail and no folders, and INBOX, special-use folders and folders that hold one are never renamed or deleted; per-run caps (`MAIL_TOOL_LIMITS`) on folder changes per account, moves and flag changes, against a runaway or talked-into run, set so that merging a few folders fits; a `reason` on every write; one `agent_actions` row per changed mail or folder. Mail is named by per-run ids such as `m12` (`mail-handles.ts`); a tool takes only ids its run listed, found again by Message-ID when the UIDs changed. `RunMailboxes` opens only the user's own accounts, serialises IMAP per account, logs in again after an idle timeout, and records each account's status at the end. Prompt-injection boundary: the main agent (Sonnet) sees headers and the descriptions of the reader sub-agent (Haiku, no tools, `read-mail-with-reader.ts`), never a mail's text.
- Organise: `src/assistant/organise/`. The 15-minute cron `organise` runs only for users with `user_settings.organise_enabled`. It opens the accounts, calls no model when no inbox holds mail, and else runs the organise agent, which reads each new mail and moves it. Its instructions (`organise-task.ts`) give the goal, the owner's `organise_notes`, which come first, and the facts it cannot see, and leave to the model how to file mail and when to make, merge or rename folders; keep them that short. They do ask for an empty inbox, because a single mail left there means a model call every 15 minutes. The owner still sees moved mail: it stays unread and the morning report covers it. Its tools are the mail tools without `mark_read` and `mark_flagged`: read state changes only when the owner reads the morning report, and the report decides what needs the owner. Mail it does not reach stays for the next run. With an iCloud account, it also gets the calendar tools and may keep the owner's calendar in step with the mail. A server with neither MOVE nor UIDPLUS gets `write_error_code` `move_unsupported` and takes no part here, because its inbox always holds mail and every run would call the model for nothing; the morning report still reads it and marks its mail read, and `move_mail` refuses on it.
- Morning report: `src/assistant/report/`. The hourly cron `morning-report` builds a user's report from their `digest_hour` on (local time, `due-report-date.ts`) once per local day, as an agent run (`run-report-agent.ts`, instructions in `report-task.ts`, keep them that short). The report covers a fixed window, from yesterday at `digest_hour` up to today at `digest_hour` on the wall clock (`reportMailWindow` in `local-day-bounds.ts`; 23 or 25 hours on a daylight saving day), never from when the build ran, so a late build or a retry leaves no gap or overlap with the next report. Changing `digest_hour` or the time zone gaps or overlaps once: mail in a gap stays unread and in no report, and mail in an overlap can be reported again. The agent gets the read-only mail tools (`list_mail` takes days in the owner's zone or exact times, and the prompt gives the window's), the calendar tools, to see today and to make the changes that the organise agent missed, the to-do tools (`agent/todos/`, which keep each change in memory) and `submit_report`; `runAgent`'s `finish` leaves the step at the step cap or after the time only `submit_report` and asks for it (the API refuses a forced tool choice and a step without thinking on Sonnet). After the run, whatever the agent did, code reads the events of the report's day (`readDayEvents`, as Home does) into `content.agenda`, so the agent's own calendar changes show. The agent adds only `eventNotes`, each kept when its event, or for a repeating event its occurrence, is in that day. A calendar that fails or takes over 30 s leaves `agenda` null, sets `content.calendarUnread` (which the page says; no calendar account does not) and does not stop the report. Before the run, code lists the window's mail of each folder that can hold it (`report-folders.ts`), and the prompt gives each folder's count. A line of needs-action can name a to-do, which the page shows in its place, so the page says each thing once. The report (`content` version 2; version 1 reports still render) and the to-do changes are stored in one transaction; only then is all of the window's mail in those folders marked read, by code, with an `agent_actions` row each. Mail from the window's end on stays unread and waits for the next report. When no mailbox can be read, there is no model, or the agent submits nothing, it stores nothing and the next hour tries again; from 23:00 local it stores a report that says so (`build-morning-report.ts`). A calendar change happens during the run and stays when the run stores nothing; the next try lists it, and `create_event` refuses a second copy. A mailbox that fails to open gets two more tries about 60 s apart in the run, unless only a new login can fix it; the organise cron does not retry, because it runs again in 15 minutes. A mailbox that is still down does not delay the report: the report warns, and the next report that can read the mailbox also lists and marks read its mail from the local midnight of the `mailDate` of the oldest report it missed, up to 7 reports back, and up to the window's end. It starts at midnight because reports from before the window covered that whole local day and the stored content cannot tell the two kinds apart, so a catch-up can report a few hours of mail again. `mailCount` stays the mail of the window, and no other account's older mail changes. Pages: `/` (Home, below), `/todos`, `/reports`, `/reports/[date]`. Web Push needs both VAPID env vars; the service worker registers in production builds only, so push cannot be tried under `pnpm dev`.
- Report preview: `report/run-report-preview.ts`, page `/report-preview`, linked from `/settings/report`. `POST /api/report-preview` (user from the session) claims the user's one row in `morning_report_previews`, answers at once and runs the real report agent in `after()` with the cron's budget, under the task `report-preview` in `agent_runs`. A second start while one runs gets a 409; a `running` row as old as the function's 800 s limit counts as failed, and every failure ends in a `failed` row, with no retry and no last try. It stores nothing else: no `morning_reports` row, no `agent_actions`, no to-do change, no mail marked read, no calendar change, no push: its agent has the same tools as a real run, but it opens `RunCalendars` with a read-only `CalendarPolicy`, so `create_event`, `update_event` and `delete_event` only refuse, saying what the preview would change in the report instead. Only the preview row keeps the content and the to-do changes the agent would make, and `readReportPreview` shows them through `ReportView` inside `TodosReadOnly`, new and closed ones included. The window is the last 24 hours ending now, not the report's fixed window, because that can hold almost no mail right after a report; the catch-up for missed mailboxes stays the same as in a real run. `today` in the prompt and the day of the agenda is the date of the next report (`nextReportDate`), and `content.mailDate` is the local date the window starts on. Mail that a real report marked read (a `mark_read` row of a `report` run, by account and Message-ID) looks unread to this agent only, through `previewMailboxSession` (`preview-mailbox-session.ts`), which `RunMailboxes.open` puts around each session of the run, so the preview is not thinner than the report. That session refuses every write to the server, so no flag changes. A mailbox's status and OAuth token can still change, as in any run that opens it.
- Home: `src/assistant/home/` and `home-page/`, page `/`. A visitor without a live session at `/` or `/zh` gets the public home page at the same address: the proxy reads the session there, on no other path, and rewrites to `(open)/public-home`, whose own path answers 404. Each render chooses a view (`chooseHomeView`): the newest report until `morning_reports.seen_at` is set, then today (the to-dos' Today and Upcoming views, as on `/todos`, and the calendar, read live from CalDAV in a Suspense boundary). `MarkReportSeen` sets `seen_at` from the browser once the document is visible, never in a render, because a prefetch must not count. The router keeps a fetched page for 5 minutes, so it refreshes once the owner goes to a different page, and `/` then shows today; a link to the page that shows (the tab, the mark, the way on from the report) also refreshes (`links/link.tsx`). A status card at the top polls `GET /api/home/status` (3 s during a run, 15 s near an organise run, 60 s else; none while hidden; `poll-delay-ms.ts`) and says what a run does from `agent_runs.progress`, else counts down the last 3 minutes before the organise cron and then checks for 90 s (`select-home-card.ts`). All its times come from the server's clock, so shifting the browser's clock does not show the countdown. A refresh chooses the view again, so the report view never refreshes in a poll, and refreshes only on a return after 30 minutes or more hidden (counted from load when the page loaded hidden). The today view refreshes when a poll sees a run end, a newest report that is unseen (once per date, in case a refresh fails or returns the same view), or an owner's local date (`HomeStatus.localDate`) that differs from the render's.
- To-dos: the report agent proposes changes with the tools in `agent/todos/`, and `applyTodoChanges` stores them with the report; the owner writes through `report/owner-todos.ts` (`/api/todos`, `/api/todos/[todoId]`, `/api/todos/[todoId]/restore`, bulk due dates all or none, which answer with what each row was, so that an undo also takes the date out of `owner_edited_fields` when it was not there before; user from the session). `created_by` says who added a row. A delete is soft: `deleted_at` hides the row from every read, and each owner update and agent change is limited to rows that are not deleted, so a needs-action line that names a deleted to-do shows its own text. The owner wins: each field the owner sets joins `owner_edited_fields`, `update_todo` refuses it and tells the model to mention the conflict in the report, and `applyTodoChanges` locks the rows in its transaction, drops those fields, and skips rows that were deleted or done during the run. Deleted to-dos do not come back: the prompt lists those of the last 30 days as `d1`, `add_todo` refuses a mail that is the source of one, and takes the same normalised title only when it names that to-do in `deletedTodo` and gives a mail received after the deletion; the new row keeps `re_adds_todo_id`, and the page says so. `start_date`, optional and never after `due_date` (the API, the agent's tools and a check constraint hold this; when the owner moves the due date before it, the page clears it), is the day a to-do joins the Today view of `/todos` and the home page, which holds what is overdue, due today or started by today; Upcoming holds the rest. On a report page, a needs-action line whose to-do starts after the report's day shows with the report's other to-dos. `position`, an identity column the agent never sees, is the owner's order: a new row takes the next value and goes last, whoever adds it, and `PUT /api/todos/order` swaps the positions that the listed rows hold, so that every other row keeps its own. `listOpenTodos` and `listTodos` order by it, and the array of rows is the order on the page, so the client has no position of its own. Today and the no-date group show that order; Upcoming sorts by date, and a row drags only among rows of its date (`orderRuns`). A row that changes group keeps its position and can land mid-list. `repeat` is the rule of a repeating to-do (`report/next-occurrence.ts`, where `nextOccurrence` is pure): it holds the day asked for, so the 31st clamps to a short month and returns to the 31st, and the next date is after both the occurrence's date and the day it was done, so a to-do done late does not come back overdue. Only the owner sets a rule, and setting one makes the due date the owner's; the agent sees it, and `complete_todo` closes that occurrence only. Closing a repeating to-do, by either of them, makes the next occurrence in the same transaction (`addNextOccurrence`): same title, detail, rule, `owner_edited_fields` and place in the order, the start date as far before the due date, no mail, `created_by` the owner's, and `next_todo_id` on the closed row. Reopening takes that row away with a hard delete, because a soft delete would tell the agent that the owner deleted it, and the reopened row takes its place; when the next occurrence is done or deleted, the reopened row stays without a rule, so the series does not run twice. A skip moves the same row to its next dates (`PUT /api/todos/[todoId]/occurrence`, which leaves `owner_edited_fields` alone). A delete ends the series, because the open row carries the rule. A to-do the agent closes keeps `done_reason`, which the Done list and the report show; the owner's close leaves it null and a reopen clears it. `OpenTodoGroups` is the input and the open rows on both `/todos` (`TodoBoard`) and the home page's today view, so a row can do the same on each. `/todos` lists the open rows and the 5 done most recently. A search (`searchTodos`, `?q=` on `/todos`, set by `TodoSearchBox` after a pause in typing and never during IME composition) replaces them with up to 50 rows, open and done, whose title, detail or a step holds the text. The box is outside the store, which has the text as its `key`, so each search starts from the server's rows, and a row that a change takes out of the search goes at the refresh. `/todos/done?page=` is the archive of what is done: 30 rows a page, by completion date in the owner's zone (`groupDoneTodos`), with its own store, so a row does the same there, and a reopen leaves the page with a message. The pages hold the list in `TodoStoreProvider` (`report-page/todo-store-provider.tsx`): each change shows at once, requests run one at a time, and a failure rolls back and says so. The client makes the id of a new to-do, so a later change can name a row that is still being sent. The router keeps each page for 5 minutes, also for back and forward, and a refresh clears them, so the store refreshes once its saves have settled (`refreshAfterSave`), also when the owner has left the page. The report on `/` waits until the owner leaves, because a refresh there would choose today instead. A page that the server rendered before the last save does not replace the list, because it can land after that save. `parseTodoDate` reads a date from quick add text, on the client, and from a capture on the server, with no model. `remind_at` is the time the owner asked for, picked in `user_settings.time_zone`, and the agent neither sees nor sets it. The 5-minute cron `todo-reminders` (`report/send-todo-reminders.ts`) sends each one that is due through Web Push: it claims the row with one atomic update that sets `reminded_at`, so that a retry or an overlapping run does not send twice, and rows that are done or deleted do not match. A crash after the claim loses that reminder; when every device failed, the claim goes back and the next run tries again. With no device to send to, a reminder still counts as sent. Writing a time that has passed counts as sent (`reminderWrite`), because a time that a repeat or an undo moved must not fire at once. The next occurrence takes the same time on the owner's clock, as many days before the due date (`nextOccurrenceReminder`), and so does a skip. A notification has the actions Done (`PATCH /api/todos/[todoId]`) and Snooze 1 hour (`POST /api/todos/[todoId]/snooze`), which the service worker sends with the session cookie; the proxy lets them through because their Referer is the worker's URL on this origin. A snooze sets `snoozed_until`, not `remind_at`, so that the next occurrence does not drift. After a button, the worker posts `TODOS_CHANGED_MESSAGE` to open pages, and `RefreshOnTodosChanged` (`pwa/`), on every signed-in page, loads them again, which also clears the cached pages. iOS shows no actions, so a tap opens `/todos`. The worker runs only in a production build. `todo_checklist_items` are the steps of a to-do, one level, in its editor (`report/owner-checklist.ts`, `/api/todos/[todoId]/checklist`): each step saves at once, with its own request, and only the box for a new step waits for Save. The row shows progress such as 2/5, and ticking every step does not close the to-do. A step's id is unique in its to-do only, because a next occurrence copies the steps with their ids and order and no ticks, so that the page can name them before a refresh. A skip also takes the ticks away, and its undo sends them back. A delete is hard: the steps hold nothing that the agent must remember, and the answer gives the position that an undo sends back. `list_todos` shows the checklist and no tool writes it. A to-do waits while `waiting_on` is set (who or what, with an optional `follow_up_date`): it has its own group in Upcoming and stays out of Today, whatever its dates, until the follow-up date. A due date does not bring it back. The owner writes a wait with `PUT /api/todos/[todoId]/waiting`, which answers with all of what it was, for the Undo. The agent has `mark_waiting`, which refuses a wait that the owner set or ended, and `reply_came`, which moves a to-do back to open, also on a wait the owner set, because that is what the owner waits for. `waiting_since` is when the wait began (the mail's time when the agent marks it): `reply_came` and `complete_todo` take only a later mail, so that a mail the owner read before marking the to-do does not end it, and `applyTodoChanges` checks this again under the lock. `waiting_note` is why the agent made it wait or ended it, which the row shows; the report lists both kinds in sections of their own (`waitingTodoIds`, `repliedTodoIds`, as they are now). The agent closing a to-do ends its wait; the owner closing one keeps it, for the Undo, and a next occurrence does not wait. Skip and Later leave the menu of a row that waits. `TodoSelectionArea`, around the open rows on `/todos` and the home page and around search results, holds the keys (`n`, `j`, `k`, `e`, `x`, `/`, `?`, read by `todoShortcutOf`, which leaves a key to a text field, an open dialog or editor, and an IME) and the selection of open rows (Select for touch, shift-click and `Space`). Focus is the place of the keys, and the DOM gives the order of the rows over their groups. `POST /api/todos/bulk` closes or deletes the rows in one transaction, all or none, and reopens or restores them for the one Undo; bulk dates go through `PATCH /api/todos`, which also takes the start date when the new due date comes before it, and answers with what both were. Closing with `next_todo_id` and reopening work as they do for one row. When the owner deletes a row with `created_by` report, one or many, the Undo toast also offers "Should not have been added", with an optional note in a sheet (`POST /api/todos/bulk`, action `reject`, all or none; with many, it covers the report's rows and gives them one note). It sets `rejected_at` and `rejection_note` on the row, a check constraint keeps them on deleted rows, and a restore clears them, so that a rejection counts only while the row stays deleted and does not return with a later delete. `/settings/report` lists them and takes one away (`DELETE /api/todos/[todoId]/rejection`). A rejected row leaves the prompt's `d1` list, which is about one matter and lets a new mail bring it back, and joins the list of the last 90 days, which is about a kind of to-do and has no ids (`readRejectedTodos`): `add_todo` refuses its title and its mail without a way round, and the agent can still say it in the report. A row menu puts time for an open to-do on the default calendar, or else the first that is not shared, when the owner has an iCloud account that does not wait for a new connect (`report/todo-calendar-slots.ts`, `/api/todos/[todoId]/calendar`): a start and a duration, picked in `user_settings.time_zone` (`CalendarSlotSheet`). This is the owner's own action, through `RunCalendars` and `ics/`, so it writes no `agent_actions` row and the agent neither sees nor sets the slot; the agent's calendar tools can change its event like any other, and the to-do then finds it changed. `calendar_account_id` says that a row holds a slot, with `calendar_url`, `calendar_href`, `calendar_etag`, `calendar_start` and `calendar_end`; the row shows these times and reads no calendar, so a change made elsewhere shows only at the next write. The event's title is the to-do's at an add or a move. The page makes the event's name, so that a retry after a lost answer finds the same event. A write sends the etag of the app's last write. An event that changed is never overwritten: the owner hears of it and can take the calendar's time (`PATCH`), and an event that now repeats or has attendees then leaves the to-do and stays on the calendar; an event that is gone leaves the to-do. A close, a delete and a skip store the to-do's change first and only then go to the calendar, so a calendar that fails loses nothing. Time to come is then freed, and a slot that has begun stays on the calendar as a record. The answer says what became of each (`freeSlotsOfClosedTodos`, `freeSlotOfSkippedTodo`), and the toast says so too. Undo puts freed time back as a new event, and a Reopen later does not. An event that changed stays there and the to-do lets it go. When the calendar gave no answer, the row keeps its slot, a closed row shows it with a way to remove it, and the 15-minute cron `todo-calendar` tries again until the slot begins; that cron also frees the time of what the report agent closed. A next occurrence has no slot, because a slot is for one occurrence; when a reopen takes a next occurrence back, the reopened row takes its slot. When the account goes, the event stays and the to-do lets it go. Two ways add from outside the app. The manifest has a Web Share Target (`share_target`, Android and others; not iOS Safari), a GET to `/todos` with `title`, `text` and `url`: the page fills quick add from them (`sharedTodoText`) and takes them out of the address, and the owner still presses Add. They stay in `next` through sign-in, so the page and the layout both redirect with the whole path. `POST /api/todos/capture` is for iOS Shortcuts and Siri, and is the one way in without a session: `{ "text": "..." }` with `Authorization: Bearer <id>.<secret>`. The proxy lets this one exact path through without a Referer. `capture_tokens` keeps only the hash of the secret; the id finds the row and the compare takes constant time (`captureTokenStore.spend`). The token can only add a to-do for its owner, and the answer holds only that to-do, as the owner's, with the date read in the owner's zone. It must never be logged or go in a URL. The limit is 60 requests an hour per token, with a fixed window on the token's row in the same atomic update as the check, and a wrong secret does not count. `/settings/capture` makes a token, shows it once, revokes it (a hard delete) and gives the steps for the Shortcut.
- Activity: `src/assistant/activity/`, page `/activity`. It lists the runs newest first, folds organise runs that changed nothing into one line per day, and tells each action in words with the agent's reason (a folder emptied into one other folder and deleted is one merge). `undoAgentActions` undoes chosen actions or a whole run, newest first, from `POST /api/activity/undo` (user from the session): a move goes back by Message-ID, read and flag changes flip back, a deleted folder comes back, a created folder goes only when it is empty, and an event goes back to `detail.previous` only when every later action on it is undone and nobody changed it between the agents' writes (`detail.undo.etag` keeps the etag after an undo); an event that the agent deleted and is back in the calendar is left as it is. An action that cannot be undone changes nothing and the rest go on; undo never deletes mail. `applyTodoChanges` writes an action for each to-do change it really makes (`add_todo`, `update_todo`, `complete_todo`, `mark_waiting`, `reply_came`), in the report's transaction, so a preview writes none. Each has the agent's reason, which `add_todo` and `update_todo` also ask for, and in `detail` (`TodoActionDetail`) what it replaced and wrote; `created_at` counts up in a report, because one transaction has one clock time and an undo goes newest first. `undoTodoAction` runs in one transaction with `undone_at`: an add is a soft delete with `add_undone_at`, which keeps it out of the prompt's `d1` list and off the rejections, and it is refused once the owner has made the to-do their own (a field, a close, a rule, a reminder, a step, a time on the calendar); an update returns each field that still holds what the action wrote and is not the owner's, and `detail.undo.kept` names the others for the page; a wait goes back whole, only while it is what the action left; a completion reopens, unless a later close replaced it, with its wait, and takes back the next occurrence as the owner's reopen does. A deleted to-do refuses, and a closed one refuses all but the undo of a completion. The organise prompt lists the mail and calendar changes that the owner undid in the last 30 days, and the report prompt the to-do changes, so that each agent does not do them again.
- Calendar: iCloud only. CalDAV goes through the `CalendarSession` interface (`src/assistant/calendar/caldav/types.ts`); `tsdavConnector` is the real one and sends the login only to `*.icloud.com`, `createFakeCalendarServer` the in-memory one for tests. Never test against a real calendar. `ics/` builds, reads and edits ICS: timed events carry a TZID per end (a flight ends in the arrival zone) with a VTIMEZONE from Intl; `editEventIcs` changes one VEVENT and keeps every other line. The agent's calendar tools (`agent/calendar/create-calendar-tools.ts`, and `create-event-write-tools.ts` for the writes) are list calendars (each marked default, from RFC 6638 `schedule-default-calendar-URL` when the server tells it, and shared), list events (by day range, each occurrence of a repeating event at its own start, `ics/events-in-range.ts`; optionally by text such as a booking reference; notes never reach the model), create (into the calendar the agent picks, else the default one), update and delete. `RunCalendars` logs in, on the first calendar call only, to the user's own iCloud accounts with the mail account's app-specific password; `CalendarPolicy` says which calendars the agent may write (`writeEveryCalendar` now; the seam for a per-calendar setting). Guardrails in the tools: per-run event ids such as `e3` (`event-handles.ts`), made only by list and create; a write sends the etag the run saw and is refused when the event changed; no change to repeating events or events with attendees (iCloud could mail the attendees); no new event that is over or that a calendar has already (same title and start, or one more from the same mail at the same time: `create_event` needs the mail, and the event keeps its Message-ID in `X-QINGQI-SOURCE-MESSAGE-ID`); per-run caps; a `reason` on every write. Each write is an `agent_actions` row (`create_event`, `update_event`, `delete_event`; the mail columns name the source mail) whose `detail` holds the calendar, href and etag, and before an update or a delete `previous: { href, etag, ics }` for undo. The reader gives the event facts of a mail (`events` in `read-mail-with-reader.ts`), so the calendar tools never need mail text.
