# Assistant

The app has one user, the owner, and stores login, settings, push subscriptions, sealed mailbox logins, what the models write (morning reports, to-dos), and what the agents do: `agent_runs` (each run's steps, with tool inputs and outputs cut short, the model's last words and its tokens) and `agent_actions` (each change to a mailbox, with the mail's Message-ID, subject, sender and folders, for an activity page and undo). These hold headers and the agent's words; mail bodies stay in the mailbox and are read from IMAP when a job needs them.

- Ports: the app is `node ../../scripts/get-worktree-port.mjs 300`, its PGlite database `… 2533`. `ASSISTANT_PORT=3000 pnpm dev` puts the app on 3000, the one localhost port the Google and Microsoft OAuth clients accept; stop `apps/web` first.
- `pnpm dev` starts a per-worktree PGlite database in `.assistant-db/`, migrates it, seeds one dev user, and sets local secrets, unless `ASSISTANT_DATABASE_URL` is set. Delete `.assistant-db/` to start over.
- Sign in as an agent: `pnpm --filter assistant assistant:session` while `pnpm dev` runs, then set the cookie it prints on `http://localhost` (a LAN host needs a Secure cookie). There is no sign-up: the owner's passkeys exist in production, and a lost passkey needs a passkey row written by hand.
- Vercel env: run `vercel link --project assistant --scope tuja-labs --yes` in `apps/assistant` once, then `vercel env run -e development -- <cmd>` there. The repo root is linked to `qingqi-dev`. A changed variable reaches production only with a new build, and the `ignoreCommand` in `vercel.json` cancels a Redeploy of a commit that did not change the app, so merge a change under `apps/assistant` instead.
- Data access: pass the user id from the session or the cron, never from a request body, and filter every query of a user table by `user_id` (`ownAccount` in `mail/accounts/own-account.ts` for one account). There is no row level security.
- Migrations: change `src/assistant/db/schema.ts`, run `pnpm assistant:generate`; write SQL drizzle cannot generate with `pnpm exec drizzle-kit generate --custom --name <name>`. Never edit or delete an applied migration: production has run them all. `0000_baseline` replaced the first 18 migrations; its journal `when` is that of the last one it replaced, and drizzle runs only migrations with a later `when` than the newest applied one, so databases that ran the old migrations skip it. A dev database from before the baseline that fails to migrate needs `.assistant-db/` deleted. Vercel runs them on preview and production builds. Previews use the Neon branch `preview`, which `assistant-reset-preview-db.yml` resets from production every day, without sign-in sessions, mail accounts and push subscriptions.
- Crons: add the route under `src/app/api/cron/`, build it with `makeUserCronHandler`, and list it in `vercel.json`. The proxy lets `/api/cron/*` through without a Referer; the handler checks `CRON_SECRET`.
- Mail: `src/assistant/mail/`. IMAP goes through the `MailboxSession` interface (`imap/types.ts`); `imapflowConnector` is the real one, `createFakeMailServer` the in-memory one for tests. The connector never sends CLOSE or EXPUNGE: CLOSE expunges mail that another client flagged `\Deleted`, so before a RENAME or DELETE it selects INBOX read-only, and imapflow then has no open folder to CLOSE. Never test against a real mailbox. Log in with `openMailboxSession` (`accounts/open-mailbox-session.ts`): when the server refuses an OAuth token, it refreshes the token and tries once more before the account goes to `reconnect`. A connect and 立即检查 run `checkAccount`, which reads the folder list and no mail.
- Local OAuth: Google and Microsoft accept only `https://assistant.qingqi.dev` and `http://localhost:3000` callbacks, so run `vercel env run -e development -- env ASSISTANT_PORT=3000 pnpm dev` to get the client ids.
- Agents: `src/assistant/agent/`. `runAgent` (`run-agent.ts`) runs one task for one user with AI SDK `generateText`, tools and `stopWhen` (a step cap and the cron's `endsAt`), and writes `agent_runs`. Tools are framework-free `agentTool`s (`agent-tool.ts`), so an MCP endpoint can wrap them too; a refusal (`ToolRefusal`) or a failed call goes back to the model as `{ error }` and never stops the run. Only tools with `loadUpFront` are in the model's context from the start; `toAiTools` defers the rest (`deferLoading`) and adds Anthropic's BM25 tool search, which loads them when the model looks for them; `runAgent` names them in the instructions, because the model does not know of them otherwise. The API needs at least one tool that loads up front, and the cache breakpoint on the last message still caches every step, because a found tool is added in the conversation, not in the prefix. The mail tools (`mail/create-mail-tools.ts`) hold every guardrail, not the prompt: MOVE only; no tool deletes mail, expunges or sends; never into Trash, Sent, Drafts or `\All`/`\Flagged`/`\Important` (Junk is allowed, `destination-refusal.ts`); a folder is deleted only when it holds no mail and no folders, and INBOX, special-use folders and folders that hold one are never renamed or deleted; per-run caps (`MAIL_TOOL_LIMITS`) on folder changes per account, moves and flag changes, against a runaway or talked-into run, set so that merging a few folders fits; a `reason` on every write; one `agent_actions` row per changed mail or folder. Mail is named by per-run ids such as `m12` (`mail-handles.ts`); a tool takes only ids its run listed, found again by Message-ID when the UIDs changed. `RunMailboxes` opens only the user's own accounts, serialises IMAP per account, logs in again after an idle timeout, and records each account's status at the end. Prompt-injection boundary: the main agent (Sonnet) sees headers and the descriptions of the reader sub-agent (Haiku, no tools, `read-mail-with-reader.ts`), never a mail's text.
- Organise: `src/assistant/organise/`. The 15-minute cron `organise` runs only for users with `user_settings.organise_enabled`. It opens the accounts, calls no model when no inbox holds mail, and else runs the organise agent. Its instructions (`organise-task.ts`) give the goal, the owner's `organise_notes`, which come first, and the facts it cannot see, and leave to the model how to file and flag mail and when to make, merge or rename folders; keep them that short. Its tools are the mail tools without `mark_read`: read state changes only when the owner reads the morning report. Mail it does not reach stays for the next run. With an iCloud account, it also gets the calendar tools and may keep the owner's calendar in step with the mail. A server without MOVE gets `write_error_code` `move_unsupported` and takes no part.
- Morning report: `src/assistant/report/`. The hourly cron `morning-report` builds a user's report from their `digest_hour` on (local time, `due-report-date.ts`) once per local day. It reads the mail of the previous local day from IMAP, read-only (`read-day-mail.ts`; Gmail only All Mail, other servers every folder but Sent, Drafts, Trash, Junk and the virtual ones, `report-folders.ts`), gives it and the open to-dos to Sonnet (`report-prompt.ts`, raise its `version` when it changes), and stores only `morning_reports` and `todos`. When no mailbox can be read, there is no model, or the call fails, it stores nothing and the next hour tries again; from 23:00 local it stores a report that says so (`build-morning-report.ts`). Pages: `/` (latest report), `/todos`, `/reports`. Web Push needs both VAPID env vars; the service worker registers in production builds only, so push cannot be tried under `pnpm dev`.
- Calendar: iCloud only. CalDAV goes through the `CalendarSession` interface (`src/assistant/calendar/caldav/types.ts`); `tsdavConnector` is the real one and sends the login only to `*.icloud.com`, `createFakeCalendarServer` the in-memory one for tests. Never test against a real calendar. `ics/` builds, reads and edits ICS: timed events carry a TZID per end (a flight ends in the arrival zone) with a VTIMEZONE from Intl; `editEventIcs` changes one VEVENT and keeps every other line. The agent's calendar tools (`agent/calendar/create-calendar-tools.ts`) are list calendars (each marked default, from RFC 6638 `schedule-default-calendar-URL` when the server tells it, and shared), list events (by day range, optionally by text such as a booking reference; notes never reach the model), create (into the calendar the agent picks, else the default one), update and delete. `RunCalendars` logs in, on the first calendar call only, to the user's own iCloud accounts with the mail account's app-specific password; `CalendarPolicy` says which calendars the agent may write (`writeEveryCalendar` now; the seam for a per-calendar setting). Guardrails in the tools: per-run event ids such as `e3` (`event-handles.ts`), made only by list and create; a write sends the etag the run saw and is refused when the event changed; no change to repeating events or events with attendees (iCloud could mail the attendees); no new event that is over or that a calendar has already (same title and start, or one more from the same mail at the same time: `create_event` needs the mail, and the event keeps its Message-ID in `X-QINGQI-SOURCE-MESSAGE-ID`); per-run caps; a `reason` on every write. Each write is an `agent_actions` row (`create_event`, `update_event`, `delete_event`; the mail columns name the source mail) whose `detail` holds the calendar, href and etag, and before an update or a delete `previous: { href, etag, ics }` for undo. The reader gives the event facts of a mail (`events` in `read-mail-with-reader.ts`), so the calendar tools never need mail text.
